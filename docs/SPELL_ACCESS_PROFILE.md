# Loaded spell-ray profiling

Opt-in development harness: `source scripts/cloud-shell.sh`, then `./gradlew runSpellAccessProfile -PprofileRevision=<exact-code-description>`. Requires isolated `run-spell-access-profile/.profile-approved-disposable`, ordinary server properties and already-ready scene chunks. It refuses connected players and does not change legal/authentication requirements. Keep the world/report/JFR files ignored. All profile classes are excluded from the player JAR.

Each of two phases uses600warmup+600measured normal server ticks:0baseline and256sixteen-block rays per tick, varying eight horizontal headings across loaded chunk boundaries and a small wall. Rays use the real SpellWorldAccess.ray and one unspawned FakePlayer for the required entity context. This measures the changed loaded-ray helper, not full spell casting, resource costs, cooldowns, live player networking or battle AI. There are no force-loaded chunks or background world reads. It deliberately does not use the idle-station profiler to claim a casting speedup.

JVM4active processors/2GiB. Runtime JSON records revision, phase counts, wall time/observed TPS, individual workload and vanilla tick-ring means/p99/max. Work is injected by a Post callback; its direct duration is separately measured. Tick-ring timings are reported as observed, not an isolated inclusive spell timer; use the direct workload metric and JFR stacks to assess the ray path. TPS over short windows may exceed20during catch-up. Compare on matched fresh flat worlds/settings, without other builds/clients/profiles running. A single pair on shared cloud hardware cannot establish a statistical speedup or long-term memory stability.

JFR profile recordings cover measured windows only, include600custom events each, and disable initial environment/system-property/JVM command-line snapshot events. Analyze with `python3 scripts/analyze-spell-access-profile.py <report.json> --jfr "$JAVA_HOME/bin/jfr"`. The analyzer requires complete phases/nonempty recordings and exactly600workload events, then reports execution samples, weighted allocation samples and GC event counts. Weighted bytes are sampling estimates, not exact allocation totals. Absence of GC events does not prove zero GC cost or leak freedom.

The baseline uses147c92e's old ray-access implementation plus the same build task/probe. Successful real-server baseline completed and the analyzer verified both600event recordings. The after comparison and integration decision are recorded in docs/INTEGRATION_REVIEW.md once executed.
